# Architecture

## Overview

BTG Packer is organized as an analysis-driven PE transformation pipeline rather than a loader that treats the original executable as one opaque blob.

```text
Input PE32+
   |
   v
PE parsing + program analysis
   |
   v
ProgramModel / CFG / function ownership
   |
   +----------------------+----------------------+
   |                                             |
   v                                             v
Native CFG path                              Program-VM path
   |                                             |
block slicing                                   x86-64 decode
layout shuffle                                  RISC lifting
branch/RIP fixups                               ownership analysis
native encoding                                 family planning
   |                                             |
   +----------------------+----------------------+
                          |
                          v
                 runtime protection
                          |
                          v
                   PE reconstruction
                          |
                          v
                     validation
```

## Public module structure

`src/lib.rs` exports the project as both an application and a library. Major areas are:

```text
src/analysis/       whole-program discovery and indirect-flow analysis
src/core/           trigger graph primitives
src/graph/          CFG/basic-block structures
src/obfuscation/    native transformation helpers
src/mba/            mixed boolean-arithmetic transforms
src/dispatcher/     generated native runtime/dispatch code
src/crypto/         crypto primitives and providers
src/pe/             PE parser, builder, relocation, TLS/unwind/load-config support
src/pipeline/       transformation orchestration and validation
src/vm/             RISC lifter, bytecode, VM families and native runtimes
src/qa/             QA corpus and compatibility testing
src/sdk/            selective virtualization interfaces
```

## Front-end and configuration resolution

`src/main.rs` is the CLI front-end. It parses `CliArgs`, converts them into a requested protection profile and calls `protection_profile::resolve()` before the transformation starts.

This is an important separation:

```text
raw CLI flags
    |
    v
RequestedConfig
    |
    | resolve()
    v
ResolvedConfig
    |
    v
PipelineContext / runtime builders
```

Consequently, documentation should distinguish between a flag being requested and a feature actually being active after conflict resolution.

The resolver handles rules such as `--full` expansion, VM-vs-native dispatcher precedence, memory-hardening compatibility, crypto prerequisites, M7 mode selection and retired RC4 rejection.

## ProgramModel

The `analysis` subsystem builds information needed before rewriting executable bytes. Its modules include dedicated analysis for:

```text
CFG seeds
code pointers
CRT structures
indirect targets
indirect-call resolution
pointer tables
switch producers/targets
value flow
program metrics
```

The ProgramModel is the canonical authority for discovered functions, blocks, metadata seeds and executable-byte ownership. Native `TriggerBlock` objects are a derived transformation view rather than the sole representation of the original program.

This distinction matters for Program-VM coverage: coverage must describe original program ownership, not merely count whatever blocks survive in a rewritten section.

## PipelineContext

`PipelineContext` carries state across transformation stages. Important categories include:

- parsed `TargetPeInfo` and program analysis;
- discovered basic blocks and trigger blocks;
- deterministic RNG state;
- shuffled native layout;
- generated `.btg` and patched PE sections;
- crypto/payload/resource/IAT metadata;
- VM module placement and bytecode information;
- ownership and VM coverage reports;
- family partitions and cross-family routes;
- validation and manifest data.

This makes the pipeline state explicit: later stages consume authoritative artifacts generated by earlier stages rather than re-deriving them from the final PE whenever possible.

## Native CFG path

The native path is implemented as multiple passes under `src/pipeline/`:

```text
pass1_slice.rs    discover/slice transformable blocks
pass2_shuffle.rs  assign randomized physical layout
pass3_encode.rs   encode transformed blocks and fix control flow
pass4_section.rs  assemble generated section representation
patch_data.rs     repair references/data affected by relocation
build.rs          construct the final protected image/runtime pieces
```

At a high level:

```text
original x86-64
    |
    v
basic blocks
    |
    v
trigger blocks / slices
    |
    v
shuffled physical layout
    |
    v
branch + RIP-relative repair
    |
    v
generated native section
```

Relative control transfers and RIP-relative memory operands cannot be copied blindly after block movement. Their location-dependent displacements must be rebuilt against the new layout.

## Program-VM path

The Program-VM path introduces an additional semantic layer:

```text
x86-64 instructions
       |
       v
RISC semantic operations
       |
       v
capability + ownership validation
       |
       v
family partition / VM ABI
       |
       v
polymorphic encoding
       |
       v
rolling-key bytecode
       |
       v
native VM runtime
```

The commercial module builder packages generated native code, build-specific tables, encrypted bytecode and VM state into the form consumed by the PE embedding path.

## Two notions of ownership

BTG needs to distinguish original-program ownership from generated-runtime placement.

Original code can be classified as VM-owned or native-owned. Generated VM runtime code, bridges and metadata are new artifacts and should not be mistaken for original native fallback. This is why the pipeline persists explicit ownership diagnostics and VM coverage metrics.

## Determinism

The pipeline keeps a seeded `StdRng` in `PipelineContext`. Build-local randomness—layout, transformation constants and VM-related randomized state—is intended to derive from deterministic seed material when `--seed` is supplied.

Determinism is useful for regression tests because it lets a crash or structural validation failure be reproduced against the same transformation choices.

## Final image

The final image may contain several generated regions depending on the profile: transformed native code, boot/runtime code, VM code/table/bytecode/state, payload data, bootstrap IAT data, route metadata and rebuilt PE directories.

The final step is not just writing bytes. Structural and capability validation checks that the generated PE and the requested protection contract agree. Commercial VM mode adds explicit virtualization coverage evidence.
