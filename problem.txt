==============================================================================
PROBLEM — --vm-oep (+--full) 전체 프로그램 가상화 부트 정합 결함 [유보]
==============================================================================

상태: OPEN (2026-08-13, Phase 2.4에서 발견·재현 확인, 수정 유보 — 근본 이슈)
심각도: Critical (--vm-oep 경로 전체가 실행 불가)

------------------------------------------------------------------------------
1. 증상
------------------------------------------------------------------------------
`--full --vm --vm-oep` (또는 `--vm --vm-oep` 단독) 로 패킹한 바이너리가
실행 즉시 크래시. 콘솔 출력 전혀 없음.

  - 비디버거 실행: exit code -1073741819 (0xC0000005 ACCESS_VIOLATION)
  - 디버거(cdb) 실행: --full의 안티디버그가 먼저 동작해 ud2(0xC000001D) 트랩
    → 안티디버그 없는 `--vm --vm-oep` 빌드로 우회해 관찰 필요

재현:
  btg-packer.exe -i test\target\release\rust_packer_test.exe -o packed.exe --vm --vm-oep
  packed.exe   → 즉시 0xC0000005

------------------------------------------------------------------------------
2. 관찰된 크래시 지점 (2026-08-13 cdb 분석)
------------------------------------------------------------------------------
실행 경로: boot stub → Program VM 진입 → lift된 OEP(mainCRTStartup) 실행
→ CRT 초기화 중 GetModuleHandleA 호출 → 그 남부에서 크래시.

  예외:    0xC0000005 (first chance)
  위치:    ntdll!RtlDosApplyFileIsolationRedirection_Ustr+0x192
  콜스택:  ntdll!LdrpPreprocessDllName
           ntdll!LdrpFindLoadedDll
           ntdll!LdrGetDllHandle
           KERNELBASE!GetModuleHandleA+0x9b
           packed+0xb2b86        ← .textb 내 호출 사이트 (VM native-call 브리지
                                    또는 네이티브 제외 블록 경유 CRT init)
  레지스터: rax=0 rcx=0 (널 역참조 양상)

즉 "VM이 OEP를 dispatch하는 것 자체"는 도달하나, VM/native-call 브리지를
거쳐 들어간 CRT/로더 코드가 OS 로더 상태(activation context / TEB·PEB
연쇄 / 스택 계약 중 하나)를 기대대로 못 얻어 죽는 것으로 보임.

------------------------------------------------------------------------------
3. 현재까지의 가설 후보
------------------------------------------------------------------------------
  H1. native-call 브리지(OP_NATIVE_CALL)의 Win64 계약 위반:
      브리지가 r12-r15에 VM 인프라를 남긴 채 네이티브를 호출
      (text_lift/mod.rs 주석상 알려진 사실). CRT startup은 비휘발성
      레지스터를 쓰므로 초기화 경로가 오염될 수 있음.
  H2. VM 진입 시 스택/정렬 계약 미스매치: OS 로더 진입 직후 CRT가 요구하는
      RSP 16B 정렬 또는 TEB(gs) 기반 로컬 스토리지 접근이 VM state
      캡처/복원 과정에서 깨짐.
  H3. 제외(exclusion) 넷의 과대 확장: panic/unwind/Once 제외 클로저가
      11,016 블록(사실상 프로그램 대부분)을 네이티브로 남김 → VM↔네이티브
      왕복이 극도로 빈번해져 브리지 결함이 초기에 발동.
  H4. (기존 보고) Once teardown: 종료 시 once.rs:166 `f.take().unwrap()`이
      None에서 패닉 — VM이 Once의 atomic/클로저 로직을 재실행해 공유 상태
      파괴. (2.2에서 lock 제외 넷은 제거했으나 구조적 SEH 제외는 유지 중)

------------------------------------------------------------------------------
4. 왜 유보하는가
------------------------------------------------------------------------------
원인이 "VM 바이트코드 의미론"이 아니라 "VM↔네이티브/OS 로더 부트 계약"
전반(브리지 ABI, 제외 넷 설계, SEH/.pdata 정합, 부트 스텁 컨텍스트 캡처)에
걸친 구조 문제일 가능성이 높아, Phase 2.4의 구축 항목(전체 .text 확장,
entry_native 제거)과 독립적으로 추적할 것.

------------------------------------------------------------------------------
5. 다음 추적 단계 (재개 시)
------------------------------------------------------------------------------
  1. packed+0xb2b86 호출 사이트 확정: 그 주소가 OP_NATIVE_CALL 핸들러인지
     네이티브 제외 블록인지 (--map/--sym-map 산출물과 대조).
  2. H1 검증: 브리지 진입/복귀 시 r12-r15·RFLAGS·스택을 덤프하는
     인스트루먼트 빌드로 CRT 호출 전후 비교.
  3. H3 완화 실험: 제외 넷을 panic 문자열 직접 참조 함수로만 축소해
     브리지 왕복 횟수를 줄였을 때 크래시 지점이 이동하는지 관찰.
  4. 최소 재현 타깃: main에서 GetModuleHandleA 한 번만 호출하는 hello급
     타깃으로 --vm-oep 패킹 후 동일 크래시 재현 여부 확인.
  5. once.rs:166 teardown 패닉은 위 부트 크래시 해결 후 실행이 종료 단계까지
     도달해야 관찰 가능 (순서상 부트 크래시가 선행 해결 대상).

추가 관찰 (2026-08-13, Phase 2.5 진행 중)
------------------------------------------------------------------------------
  `--vm`(non-OEP, KSA/PRGA VM만) 경로의 패킹 산출물도 실행 즉시
  0xC0000005로 크래시한다 (출력 없음). cdb 관찰: ntdll!_chkstk → 예외 디스패치
  (RtlDispatchException/KiUserExceptionDispatch) 중 크래시 — --vm-oep의
  GetModuleHandleA 부트 크래시와는 다른 양상(스택 프로브/예외 전달 경로 손상).
  **main 기준선에서도 동일 재현** → threaded-dispatch(2.5) 회귀가 아니라
  기존 부트/VM 통합 결함 계열. 샘플 타깃 실행 검증(Phase 3)은 이 계열
  해소 후 진행 가능. (2.5의 --vm-bench 속도 개선은 --vm-test/native VM
  경로로만 검증됨 — 패킹 산출물 실행은 유보.)

  [수정 완료 2026-08-13] --vm 패킹 즉시 크래시의 근본 원인:
  v14(scan.rs gather_runs)가 **원본 .text 전체를 boot-decrypt run으로 등록해
  암호화**했는데, PE 로더는 **TLS callback을 엔트리(부트 스텁)보다 먼저 실행**
  하므로 콜백이 암호문을 실행해 0xC0000005. 수정: .text run 제거 → .text를
  설계 의도대로 평문 "안전 복사본"으로 유지 (TLS/CRT/native-bridge 경로).

  [수정 완료 2026-08-13] test [9] "System allocator may not use TLS with
  destructors" abort (0xC0000409) 근본 원인: **TLS raw-data 템플릿
  [StartAddressOfRawData..EndAddressOfRawData)이 protected에 없어 v14 부트-
  복호화 런이 암호화**했다. 로더는 프로세스 시작 시(부트 스텁 전) 이 템플릿을
  모든 스레드의 TLS 슬롯에 복사하므로, std의 #[thread_local] 정적(DTORS
  RefCell<Vec> — borrow 카운터가 slot+8)이 암호문으로 초기화되었다. [9]의 첫
  thread_local!-with-dtor 등록(mpsc/thread::spawn)에서 가비지 borrow 카운터를
  읽어 try_borrow_mut() Err → std::rt abort. 수정: patch_data.rs
  collect_protected_rva_ranges에 TLS 템플릿 범위 추가 → --vm/--chained-crypto
  패킹 exe가 [1..9] 통과.

  [잔여 2026-08-13] test [10] SEH unwinding & catch_unwind: 0xE06D7363(C++
  예외) unhandled 크래시. 근본 원인: catch_unwind가 설치한 SEH 핸들러가
  stage_exceptions의 프레임에 등록되는데, 그 프레임은 셔플 블록(.textb,
  RVA 0x44000+)이라 .pdata RUNTIME_FUNCTION 커버리지 밖이다. 원본 .text의
  .pdata 항목은 보존되지만 실행 코드는 .textb에 있으므로 OS unwind가 catch
  frame까지 도달하지 못한다. → 빌드 블록용 .pdata/UNWIND_INFO 생성 필요
  (블록별 stack frame 상이 → 단일 RUNTIME_FUNCTION 불가). plan.txt P0 10단계
  (VM-OEP/native ABI/SEH 안정화)의 핵심 항목.

  [심층 분석 2026-08-13] SEH 수정 시도 결과:
  1) per-block .pdata(virtual-Begin, 원본 UNWIND_INFO 재사용) — **로더 거부**
     (Begin = textb - 함수오프셋이 이미지 밖으로 나가 STATUS_INVALID_IMAGE_FORMAT).
  2) 함수 연속 레이아웃(각 함수 블록을 .textb에서 주소순 연속 배치) + per-function
     .pdata(원본 UNWIND_INFO 재사용, 이미지 내 범위) — **부분 진전**: 예외가
     "처리"되어 0xE06D7363 미처리 → 0xC000001D(명령 중간 점프)로 변화.
     하지만 catch 복귀 주소가 여전히 어긋나 크래시.
  → 남은 블로커: 컴파일러가 생성한 SEH 메타데이터(**FuncInfo/catch table**)
    이 원본 함수 주소/오프셋을 참조하는데 블록 셔플이 코드를 이동시켜
    catch-unwind 복귀 타깃이 깨진다. 완전 수정 = 셔플 코드용 SEH 메타데이터
    재작성(또는 SEH 함수 비셔플). 이는 plan.txt P0 "SEH 안정화"의 큰 작업.
    (함수 연속 레이아웃은 셔플 세분도를 낮춰 보안 회귀이므로 원복함 —
     현재 트리는 --vm 패킹 [1..9] 통과 상태 유지.)
