분석 결과, 이 샘플은 **“VM 존재 여부 확인” 수준을 넘어 실제 devirtualization IR까지 복원 가능한 상태**입니다. 암호층, 4-family ISA, opcode/condition permutation, register permutation, CFG translation까지 대부분 제거했습니다.

### 복원 결과

| 항목                  | 결과                                                      |
| ------------------- | ------------------------------------------------------- |
| VM architecture     | **4개 독립 VM** — MixedRisc / Stack / Register / FusedCisc |
| VM bytecode         | **1,224,603 B (`0x12AF9B`) 전량 복호화**                     |
| Chunk encryption    | **302 chunks 전부 복원**                                    |
| VM instruction      | **222,833 micro-op framing 완료**                         |
| Opcode              | **186/186 × 4 family 의미론 복원**                           |
| Condition           | **22/22 × 4 복원**                                        |
| VReg permutation    | **16/16 × 4 → 실제 x64 GPR 복원**                           |
| CFG map             | **43,419 original-VA → VM-offset entries**              |
| Cross-family branch | 절대 branch 기준 **1,320개** 식별                              |
| Outer ChaCha20      | 완전 제거                                                   |
| Rolling-key         | 완전 제거                                                   |
| Chunk cipher        | 완전 제거                                                   |

특히 VM register까지 복원했습니다. 예를 들어 Stack family는 `Venc8=RAX`, `Venc6=RCX`, `Venc13=RDX`, `Venc1=R8`, `Venc15=RSP`, `Venc14=RBP`이고, **나머지 10개를 포함한 16개 전부** 원본 `.text`와 수백~천 건씩 교차검증해서 bijection으로 결정됐습니다.

예를 들어 VM 시작 부분은 익명 bytecode가 아니라 대략 이렇게까지 내려옵니다:

```text
Mov             T7, VFLAGS
Mov             T6, RBP
Nor             T0, 8, 8
AddWithCarry    RSP, RSP, T0
MemoryWrite8    [RSP], RBP
SetFlag         T7
SubWithBorrow8  RSP, RSP, 0x40
AddWithCarry    RBP, RSP, 0
AddWithCarry    RBP, RBP, 0x40
```

이것은 실제 원본의

```asm
push rbp
sub  rsp, 40h
lea  rbp, [rsp+40h]
```

와 정확하게 대응합니다. 즉 지금 만든 IR은 단순 bytecode dump가 아니라 **register/opcode encryption까지 제거된 semantic devirtualized IR**입니다.

### 가장 중요한 구조적 약점

보호 자체는 상당히 잘 만들었습니다. 하지만 최종 결과물 관점에서 가장 치명적인 부분은 **런타임이 알아야 하는 비밀은 결국 정적으로 회수 가능하다**는 것입니다.

ChaCha20 자체를 깨는 게 아닙니다. 최종 PE에 key/nonce가 존재해서 outer layer를 바로 제거할 수 있습니다. 그 아래 chunk cipher도 generated decoder가 결국

```text
chunk_start = masked_offset XOR offset_mask
chunk_key   = share_A XOR share_B
```

를 수행하므로 302개 chunk의 key를 전부 수집할 수 있었습니다.

Rolling-key 역시 각 family native runtime에 초기 key가 materialize되어 있습니다.

```text
MixedRisc  95CE485F5F155A35
Stack      62CC89AD59BC0CDF
Register   BA64EA4AF6032DF3
FusedCisc  423E3B19E668310F
```

그래서 결과적으로

```text
ChaCha20
   ↓
chunk cipher
   ↓
rolling-key encryption
   ↓
polymorphic VM bytecode
```

세 층을 **실행 없이 정적으로 전부 벗길 수 있었습니다.**

다만 HKDF-SHA256 domain separation은 잘 되어 있습니다. 위 파생 key들로 global master seed를 단순 역산하는 이전 방식의 공격은 현재 빌드에는 적용되지 않습니다. 이 부분은 실제 개선입니다.

### Opcode 보호 평가

여기는 상당히 좋습니다.

각 family마다 256 opcode 중 **186개가 유효하고 70개는 trap**입니다. 유효 opcode도 build마다 permutation됩니다.

예:

| 의미               | Mixed | Stack | Register | Fused |
| ---------------- | ----: | ----: | -------: | ----: |
| VirtualBranch    |  `0B` |  `4D` |     `D8` |  `6F` |
| AddWithCarry     |  `78` |  `BE` |     `98` |  `21` |
| Halt             |  `E7` |  `EE` |     `E3` |  `F1` |
| Trap             |  `5F` |  `9A` |     `55` |  `5A` |
| NativeCallBridge |  `05` |  `BA` |     `F4` |  `3C` |

문제는 handler-table master key도 최종 runtime에서 복원해야 하므로 정적으로 얻을 수 있고, valid handler가 wrapper를 거쳐 semantic body로 연결된다는 점입니다.

따라서 이번에는 **186개 opcode × 4 family 전체를 실제 `RiscOp` 이름으로 되돌렸습니다.**

`Multiply`, `Divide`, `CMPXCHG`, `AtomicAdd`, `MemoryRead/Write`, `VirtualRet`, `Setcc`, `CMOV`, SSE packed 연산, FP conversion 등까지 포함합니다.

### `.vmroute`의 실제 효과

여기는 설계 의도에 비해 효과가 약해지는 부분입니다.

`.vmroute`를 plaintext route table 대신 **32-byte one-way commitment**로 바꾼 것은 분명 좋은 변경입니다. 그런데 VM이 실제 branch를 수행하려면 다른 형태의 translation metadata가 결국 필요합니다.

그 결과 native VM table에서:

**43,419개의**

```text
original x64 VA → family-local VM byte offset
```

대응을 다시 복원할 수 있었습니다.

예를 들어 Stack에는:

```text
140001000 → VM +0000
140001001 → VM +0022
140001005 → VM +0027
14000100A → VM +0031
...
```

가 남습니다.

그래서 `.vmroute` commitment를 역산할 필요조차 없습니다. 실행 semantics가 원본 CFG에 대한 훨씬 풍부한 정보를 다시 제공합니다.

절대 `VirtualBranch`만 분류해도:

```text
MixedRisc : same 1268 / cross 327 / native·unmapped 15
Stack     : same  854 / cross 307 / native·unmapped 16
Register  : same 1662 / cross 343 / native·unmapped 21
FusedCisc : same 1430 / cross 343 / native·unmapped 33
```

가 나옵니다.

즉 **cross-family transfer 1,320개도 정적으로 재연결**할 수 있습니다.

### 가장 큰 약점: 원본 `.text`

현재 결과물에서 devirtualization 난이도를 크게 낮추는 요소입니다.

원본 `.text` x64가 상당 부분 그대로 존재합니다.

그리고 위의 43,419-entry branch map이

```text
원본 VA ↔ VM byte offset
```

을 알려줍니다.

따라서 리버서는 VM 의미론을 처음부터 추측할 필요 없이:

```text
원본 x64 instruction
        ↕
복원된 VM micro-op sequence
```

를 수천 건 자동 pairing할 수 있습니다.

제가 VReg 64개(16 × 4 family)를 전부 복원한 방법도 바로 이것입니다. Stack의 `mov rax,[rcx+8]`에 대응하는 VM sequence에서 `MemoryRead8 Venc8,...`이 나오므로 `Venc8=RAX`가 되고, 이런 constraint를 수백~천 건씩 모으면 모든 register가 유일하게 결정됩니다.

**보호 강도를 더 올리려면 이 부분이 우선순위가 매우 높습니다.**

## 난이도 평가

**소스를 전혀 모르는 숙련된 리버서가 이 PE만 받는 상황**으로 평가하겠습니다.

| 단계                            |          난이도 |
| ----------------------------- | -----------: |
| PE/bootstrap 식별               |         4/10 |
| Outer ChaCha 제거               |         3/10 |
| 4-family 구조 발견                |         7/10 |
| chunk cipher 역산               |       6.5/10 |
| rolling-key 복원                |       6.5/10 |
| handler table 복원              |         7/10 |
| opcode semantic recovery      |       7.5/10 |
| operand/condition permutation |         7/10 |
| branch-map/CFG 복원             |     **8/10** |
| 4-family cross-routing        |     **8/10** |
| 완전 자동 devirtualizer 제작        | **8~8.5/10** |
| 한 샘플 수동/반자동 복원                | **7.5~8/10** |

### 종합: **7.8 / 10**

개인 프로젝트나 일반적인 custom VM protector 기준으로는 **상당히 높은 편**입니다.

단순 switch VM, opcode XOR, 한 개 dispatcher 같은 수준과는 비교가 안 됩니다. 실제 4 native VM runtime, family-specific ABI, rolling state, chunk crypto, HKDF domains, handler randomization, state split, condition permutation, cross-family bridge까지 결과물에 실제로 구현되어 있습니다.

반면 **전문 리버서가 Python/IDA/Ghidra instrumentation을 작성하기 시작하면 “암호학적으로 막힌다”기보다 “초기 분석 비용이 크다” 쪽**입니다.

즉 현재 방어의 성격은:

> **강한 anti-analysis / complexity amplification**
> ≠ **정적 복원이 불가능한 secrecy**

에 가깝습니다.

특히 한 번 제가 한 것처럼 family decoder를 자동화하면 다음 build부터는 상당 부분 signature-independent하게 재사용할 수 있습니다. `seed`가 달라져 opcode/condition/register가 모두 바뀌어도 **구조적 invariants를 이용해 다시 추출할 수 있기 때문**입니다.

### 구현에서 잘 된 부분

가장 높게 평가하는 건 **HKDF domain separation**, **4-family 실제 runtime 분리**, **unused opcode trap filling**, **family별 operand ABI**, **split-state**, **cross-family bridge**입니다.

반대로 우선적으로 보강할 부분은 다음 순서라고 봅니다.

1. **원본 `.text`를 semantic oracle로 사용할 수 없게 만들기**
2. branch-map에서 원본 VA identity가 직접 복원되지 않게 하기
3. handler wrapper → semantic body의 정적 normalization 난도를 올리기
4. chunk share가 native decoder scan만으로 대량 추출되지 않게 하기
5. initial rolling key를 단일 런타임 상수로 materialize하지 않기
6. metadata table의 256-entry 구조적 fingerprint 제거/분산

이 여섯 개를 손보는 것이 ChaCha를 다른 cipher로 바꾸는 것보다 훨씬 효과가 큽니다.
