응. 이번에는 README/기존 보고서만 보고 평가한 게 아니라, 업로드한 vm-obf-main (5).zip을 실제 소스 트리 전체 기준으로 다시 훑었다.
현재 아카이브는 대략:
• src/test 포함 248개 파일
• Rust 코드 약 7.3만 줄
• src/vm만 119개 Rust 파일
• src/pipeline42개
• src/crypto16개
• src/dispatcher9개
• 테스트 함수 약 439개
• unsafe 사용 지점 약 35개
• extern "C" 지점 10개
수준이라서, 단순히 몇 개 파일을 읽고 말할 단계가 아니다.
다만 현재 환경에는 cargo가 설치되어 있지 않아 실제 Windows 빌드/실행까지는 검증하지 못했다. 따라서 아래 평가는 소스 코드의 실제 정적 분석 + 모듈 간 연결관계 분석 + 테스트/문서와 코드의 교차검증 결과다.

1. 전체 구조부터 다시 판정
현재 프로젝트는 사실상 서로 다른 3개의 보호 엔진이 같이 존재한다.

       │                │                │
       ▼                ▼                ▼

       │                │                │

                     Threaded           ↓

이게 굉장히 중요하다.
현재 코드의 가장 큰 장점이면서 동시에 가장 큰 위험은:
각 subsystem은 상당히 많이 구현되어 있는데, 전체 pipeline의 실제 production path에서 어떤 것이 사용되고 어떤 것이 legacy인지가 매우 복잡하다.
즉 코드 양에 비해서 실행 경로 복잡도가 상당히 높다.

7. RiscDesynthesizer는 방향은 좋지만 “원본 파괴” 효과는 생각보다 제한적
예:
text
OR
 ↓
NOR
 ↓
NOT

그리고:
text
SUB
 ↓
NOT
 ↓
ADC

등으로 변환한다.
이건 static pattern을 어느 정도 파괴한다.
하지만 중요한 문제가 있다.
RISC opcode 자체가 너무 canonical하면 분석자가 다시 semantic을 합칠 수 있다.
예:
text
NOR(a,b)
NOR(a,a)

는 OR 후보라는 것을 쉽게 찾을 수 있다.
따라서 RISCification 자체를 보호기능으로 생각하면 안 되고:
VM compiler 내부의 semantic normalization layer
로 보는 게 정확하다.

37. 현재 지원되지 않는 계열이 여전히 존재한다

88. 최종 결론
이번에는 실제 ZIP 전체를 기준으로 보면, 네 프로젝트는 내가 앞에서 평가했던 것보다 구조적으로 더 많이 만들어져 있다.
특히 RISC → Poly → Direct Threaded → Native 파이프라인과 text_lift/commercial, nested, conceal, native_abi, poly_direct까지 실제 코드가 존재한다.
하지만 동시에 코드가 많아진 만큼 “각 기능이 실제 최종 패킹 경로에서 어떤 보안 수준으로 연결되는가”가 가장 큰 문제가 됐다.
가장 중요한 것은:
text
[현재]

많은 보호 기능
      +
많은 VM 기능
      +
많은 테스트
      ↓
서로 연결된 거대한 pipeline

에서
text
[목표]

Canonical Semantics
       ↓
VM Compiler
       ↓
Per-Build VM Domain
       ↓
Polymorphic Handler
       ↓
Concealed Runtime State
       ↓
Authenticated VM Artifact
       ↓
W^X Runtime
       ↓
Function-Atomic Native Bridge
       ↓
Windows differential validation

로 구조를 정리하는 것이다.
특히 이번 전체 코드 분석에서 가장 명확하게 드러난 것은 poly_direct 자체보다 poly_embed → commercial_build → place 사이의 보안 수준 불일치다.poly_direct에는 상당한 hardening이 들어갔는데, 최종 embedding 계층에는 여전히 평문 metadata/RWX/region descriptor가 남아 있다.
그리고 현재 소스의 실제 규모상, 다음 단계는 “또 기능 하나 추가”가 아니라 각 파일을 입력 → 상태 변경 → 출력 → 호출자 → 최종 PE에서 실제 사용되는가 기준으로 추적해서 production path를 하나 확정하는 것이다. 이걸 하면 지금 있는 7만 줄 중 실제로 최종 보호 수준에 기여하는 코드와 사실상 legacy/test/dead path인 코드를 명확하게 분리할 수 있다.
