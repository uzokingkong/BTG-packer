1m 15s 동안 처리함

분석해봤어. 이번 ZIP은 단순한 “VM 흉내” 수준은 이미 지났고, RISC de-synthesis → polymorphic bytecode → rolling-key self-decoding → native handler execution → PE/crypto boot layer까지 갖춘 꽤 큰 보호 프레임워크야. Rust 소스만 약 76,118줄이고 VM 계층만 해도 legacy VM / RISC VM / poly VM / threaded VM / poly-direct commercial VM이 병존한다.

다만 중요한 결론은 이거야.

현재 --vm-commercial의 실제 production 실행경로만 놓고 보면, 기능 수는 상당하지만 아직 “Themida급 상용 VM 아키텍처”라고 부르기는 어렵다.

가장 큰 이유는 암호화 강도가 아니라 VM의 메타구조와 실행 skeleton이 한 샘플을 분석하면 너무 많이 드러나는 구조이기 때문이다.

공개적으로 확인 가능한 Themida/Code Virtualizer의 현재 버전은 2026년 8월 11일 기준 3.2.6.0이고, Oreans는 같은 VM 종류를 두 번 사용해도 register 위치, handlers, opcode table 등이 달라지며, 더 나아가 TIGER/LION 같은 VM들은 서로 다른 VM architecture라고 설명한다. 최신 버전에서도 VM register randomization과 VM instruction reordering을 계속 강화하고 있다.

3. 그런데 첫 번째 핵심 약점: 결국 ISA skeleton은 하나다

여기가 Themida와 가장 크게 갈리는 부분이다.

현재 VirtualIsaSpec::from_seed(seed)가 하는 핵심은 대체로:

↓

↓

↓

이다.

즉 build A:

0x23 → NOR
0x94 → ADD
0x61 → MOV

build B:

0xA1 → NOR

0xD7 → MOV

식으로 달라진다.

좋다.

하지만 역분석자 입장에서는 결국 둘 다:

same RiscOp universe
same operand model
same state model
same handler semantics
same decode architecture

이다.

즉 현재 polymorphism은 주로

encoding polymorphism

이다.

Themida/Code Virtualizer가 공개적으로 강조하는 건 훨씬 강한 개념이다.

Oreans 설명상 동일 TIGER VM 내에서도 매 build마다 registers, instruction handlers, opcode table 등이 변하고, TIGER와 LION 같은 서로 다른 VM은 아예 architecture 자체가 별개라고 한다.

BTG-RISC architecture
├─ seed A encoding
├─ seed B encoding
├─ seed C encoding
└─ seed D encoding

이다.

Themida 쪽 공개 모델은 개념적으로:

Architecture A
├─ CPU A1
└─ CPU A2

Architecture B
├─ CPU B1
└─ CPU B2

Architecture C
└─ CPU C1

에 더 가깝다.

이 차이가 엄청 크다.

9. 현재 commercial ABI가 너무 명확하다

commercial_build.rs 주석 자체가 현재 runtime ABI를 그대로 설명한다.

R8 = bytecode base
R12 = VIP
R13 = virtual stack
R14 = rolling key
R15 = handler table
RDX = state

이게 생성된 최종 바이너리에서도 안정적으로 유지된다면 역분석자 입장에서는 큰 선물이다.

한 샘플 분석 후 다음 샘플에서도:

find R15 table access
find [R8+R12]
find R14 update

를 찾으면 된다.

Themida 최신 release notes에서조차 VM register randomization을 계속 강화하고 있다고 명시하는 이유가 이 부분이다.

10. RegisterAssignment는 있는데 production ABI에는 충분히 반영되지 않는다

RegisterAssignment::from_seed_and_block()

이건 원래 아주 좋은 방향이다.

개념적으로:

KEY = R14
TABLE = RBX

block 2:
VIP = R11
KEY = R8
TABLE = R13

block 3:
VIP = RSI

처럼 만들어야 한다.

게다가:

까지 구현되어 있다.

즉 블록 사이 register permutation 전환기도 이미 존재한다.

그런데 실제 production commercial dispatcher의 핵심은 여전히:

R8/R12/R13/R14/R15/RDX

라는 안정적인 ABI를 사용한다.

이 코드를 제대로 연결하면 공격 난도가 꽤 크게 오른다.

11. Handler table concealment는 꽤 잘 되어 있다

이건 예전 버전보다 상당히 좋아졌다.

예전 보호기에서 흔한 약점:

handler_table[i] ^= master_key

라면 하나의 handler pointer만 알아도:

master_key

를 구해서 테이블 전체를 풀 수 있다.

현재는:

K(op) =
op*C1
^ op<<17
^ C4
^ master

를 사용한다.

그래서:

table[0] ^ K(0)
table[1] ^ K(1)
table[2] ^ K(2)
...

이다.

게다가 unused slot:

→ UD2 trap handler

이다.

그리고 encrypted table 자체 checksum 검사도 있다.

이 부분은 괜찮다.

───

12. 다만 이것도 근본적인 방어는 아니다

공격자는 table을 정적으로 풀 필요가 없다.

dispatcher에서:

xor rax, rcx
jmp rax

직전에 breakpoint/DBI를 잡으면:

opcode
resolved handler

를 그대로 수집할 수 있다.

즉:

table encryption

은 static analysis 비용을 늘려주지만

runtime semantic extraction

을 막지는 못한다.

상용 VM에서 더 중요한 건:

handler address를 숨기는 것보다 “handler 하나의 의미를 독립적으로 정의하기 어렵게 만드는 것”

이다.

18. Bytecode rolling key는 상당히 발전했다

예전 단순:

byte ^= key & 0xff

형태가 아니다.

현재는:

↓
position dependent rotations
↓
64-bit multiplication
↓
folding
↓
keystream byte

그리고 state evolution도:

previous key
• plaintext byte
• VIP
• multiply
• rotate

에 의존한다.

좋다.

특히 plaintext feedback 때문에 bytecode 중간에서 decode를 시작하려면 현재 key state를 알아야 한다.

19. 하지만 rolling key에 과대평가하면 안 된다

역분석자가 native sub_decrypt를 lift하면:

를 그대로 복제할 수 있다.

그러면 전체 bytecode decoder를 만든다.

즉 cryptographic complexity를 계속 올리는 것보다:

key evolution
+

+
branch history
+
semantic results

를 결합하는 편이 더 의미 있다.

여기서 아까 발견한 미사용 StateMachineDecoder가 중요해진다.

현재:

K[n+1] = F(K[n], plaintext, VIP)

이다.

처럼 decode state와 execution state가 서로 얽히는 구조다.

다만 이건 안정성과 random-access branch를 크게 어렵게 하므로 가장 나중에 넣어야 한다.

21. 현재 branch map도 분석자에게 메타정보를 준다

개념:

count
[target, bytecode offset]
[target, bytecode offset]
[target, bytecode offset]
...

이다.

역분석자가 이 영역을 찾으면:

virtual CFG

복원에 큰 도움을 받는다.

따라서 branch_map은 현재 꽤 큰 metadata oracle이다.

22. 이건 table layout jitter만으로 부족하다

25. Native bridge는 상당히 많이 발전했다

여기 생각보다 코드가 많다.

특히 poly_direct의 native bridge 부분에서:

VM registers → native registers
stack arguments
callee saved registers
XMM argument handling
integer return
FP return
VM state restoration

을 처리하려는 코드가 있다.

예전에 반복적으로 문제가 있었던 VM ↔ native ABI 경계를 상당히 의식해서 구현했다는 게 보인다.

이건 실제 protector에서는 매우 중요하다.

───

26. 하지만 여전히 full virtualization coverage가 아니다

text_lift/commercial.rs가 명시적으로:

RISC-unliftable
or
poly-unencodable
→ entire function stays native

정책을 쓴다.

안정성 관점에서는 아주 올바른 결정이다.

하지만 보호강도 관점에서는 공격자가:

VM ↔ native boundary

를 이용해 구조를 이해할 수 있다.

특히 native 함수가 자주 섞이면:

virtualized region
→ bridge
→ recognizable compiler output
→ bridge
→ VM

패턴이 생긴다.

───

27. FP와 특수 instruction이 바로 이 문제를 만든 흔적도 보인다

소스에:

Float scalar operations
REP/string
SEH
panic/unwind
setjmp
TLS
indirect branches

등을 별도로 처리한 흔적이 굉장히 많다.

이건 나쁜 게 아니라 오히려 실제 protector 개발에서 필연적인 단계다.

Themida도 최신 changelog에서 최근까지:

REP string opcode virtualization 개선
x64 exception handling 개선
relocation processing 개선
entry point virtualization 개선

등을 계속 수정하고 있다. 즉 이런 호환성 문제는 상용 제품도 끝없이 다루는 영역이다.

───

28. SEH / unwind는 아직 중요한 Tier-0 영역이다

현재:

text_lift/exclusions/seh.rs
panic_unwind.rs
setjmp.rs
tls_guard.rs

처럼 제외 시스템이 있다.

이는 안정성은 높여주지만 VM coverage를 낮춘다.

특히 x64 Windows는:

.pdata
UNWIND_INFO
SEH
stack unwind
C++ EH
Rust panic

가 VM과 충돌하기 쉽다.

Themida급으로 가려면 단순히 “SEH 함수 제외”를 줄이는 것보다 VM 자체가 unwind semantics를 제대로 소유하는 구조가 필요하다.

이게 진짜 어려운 Tier 0다.

───

29. 현재 anti-debug는 상용 제품 대비 얕다

dispatcher/antidebug.rs

실제 검사:

PEB.BeingDebugged
PEB.NtGlobalFlag
ProcessHeap.Flags

세 개다.

72-byte 고정 shellcode이기도 하다.

정확히 말하면 이건 기본적인 anti-debug bootstrap이지 Themida류의 anti-analysis subsystem과 비교할 수준은 아니다.

Oreans 공식 비교표 자체가 Themida에 anti-debug, monitor detection, multiple startup protection checks 등이 별도 기능으로 들어간다고 명시한다.

여기는 단순히 검사를 더 많이 추가하는 문제라기보다, 보호 시스템 본체와 anti-analysis 계층을 분리해서 설계하는 게 중요하다.

───

30. 72바이트 고정 shellcode는 signature 문제도 있다

주석에:

ANTI_DEBUG_SIZE = 72

이고 instruction sequence도 고정이다.

따라서 build마다 달라도:

GS:[60]
BeingDebugged
NtGlobalFlag
ProcessHeap

sequence가 거의 그대로 나온다.

상용 protector를 목표로 한다면 이 부분은 “더 공격적인 anti-debug”가 아니라 고정 signature를 만들지 않는 build-time code generation 관점에서 개선하는 편이 적절하다.

───

31. Crypto subsystem은 생각보다 잘 갖춰져 있다

여기는 꽤 크다.

Themida 공식 기능표에서도 whole-application encryption, runtime strings, integrity protection 등이 virtualization과 별도 보호계층으로 존재한다.

즉 BTG 방향도 맞다.

───

32. 그런데 VM 보안과 파일 암호화 보안을 분리해서 평가해야 한다

아무리:

ChaCha20
Poly1305
integrity
encrypted descriptors
encrypted bytecode

를 잘 넣어도 VM이 실행되면 결국:

bytecode semantics
handler semantics
VM state

가 runtime에 존재한다.

그래서 protector 난이도의 핵심은:

암호 알고리즘 강도

가 아니라

runtime semantic reconstruction cost

다.

이 관점에서는 아직 개선 여지가 크다.

───

33. region descriptor encryption도 암호학적 보안보다는 concealment다

embed_hardening.rs:

bytes[i] ^= key_bytes[i % 8].wrapping_add(i as u8)

이다.

이건 cryptographic encryption이라기보다는 metadata obfuscation이다.

descriptor concealment 용도로는 괜찮다.

하지만 source의 다른 ChaCha/Poly1305 계층과 같은 의미의 보안이라고 생각하면 안 된다.

───

34. seed_lifecycle도 좋은 방향이지만 master dependency가 있다

현재:

VmDomainKey
+
RegionSalt
↓
derive_seed()
↓
PolySeed

이다.

좋다.

즉 각 region이 같은 seed를 직접 갖지 않는다.

그러나 결국 한 process 내에서:

master/domain key → all VM configuration

관계가 너무 강하면 master derivation을 찾은 뒤 여러 metadata가 연쇄적으로 드러날 수 있다.

따라서 architecture configuration을 모두 하나의 seed tree에 매달기보다는 domain separation을 더 엄격히 하는 게 좋다.

예:

K_opcode
K_context
K_dispatch
K_handler_codegen
K_branch
K_metadata

를 논리적으로 별도 domain으로 관리하는 식이다.

───

35. 현재 DispatchPermutation도 구현은 좋지만 production impact를 따져야 한다

dispatch_perm.rs

이건:

opcode → handler slot

을 seed 기반 permutation으로 바꾼다.

하지만 commercial poly ISA 자체도 opcode randomization을 하고 있다.

따라서 이 계층을 단순히 하나 더 넣는다고 분석 난도가 선형적으로 올라가지는 않는다.

더 필요한 건:

opcode ID randomization

보다

dispatch architecture randomization

이다.

───

36. Nested VM도 구현 흔적은 있지만 실제 상용 engine에서는 아직 약하다

vm/nested.rs

VmCallBridge

라는 좋은 abstraction이 있다.

개념적으로:

VM A
↓
snapshot state
↓
VM B
↓
restore
↓
VM A

가 가능하다.

하지만 native commercial handler 쪽에서 VmCallBridge의 완전한 nested-runtime execution은 제한적이고, 일부 경로는 no-op/bridge semantics에 머문다.

즉 진짜:

VM architecture A
invoking
VM architecture B

는 아직 production 핵심이 아니다.

───

37. Themida와 비교하면 이게 중요하다

Oreans는 여러 VM architecture를 선택할 수 있고, 같은 application에 여러 CPU/VM을 사용할 수 있다고 설명한다. 같은 architecture라도 CPU마다 registers/handlers/opcode table이 달라진다.

현재 BTG는:

multiple VM implementations exist in source

는 맞다.

하지만 최종 protected binary에서:

multiple truly independent architectures

가 적극적으로 섞이는 구조와는 다르다.

39. 가장 먼저 고쳐야 하는 P0

우선순위 변경 이유

P0-1 production dispatcher decentralization 중앙 dispatcher가 최대 분석 anchor
P0-2 production context offset randomization 현재 state layout이 너무 안정적
P0-3 block별 VM-role register permutation R8/R12/R14/R15 fingerprint 제거
P0-4 StateMachineDecoder 실제 runtime 통합 opcode→handler 정적 관계 약화
P0-5 branch metadata representation 개선 현재 branch map이 CFG oracle
P0-6 commercial backend handler-gap CI 강제 semantic silent failure 절대 방지

내가 하나만 고른다면 P0-1이다.

43. P3는 per-region architecture selection

그 다음:

→ RISC VM

44. 그 다음 handler generator가 필요하다

architecture뿐 아니라 handler implementation도 만들어야 한다.

개념:

Semantic ADD
│
├─ Template A: ADD
├─ Template B: SUB/NEG
├─ Template C: MBA
├─ Template D: split helper
├─ Template E: temp-state
└─ Template F: fused with next op

그리고 build seed로 하나를 고른다.

더 발전하면 handler 자체를 fixed template에서 꺼내는 게 아니라:

semantic IR
↓
rewrite rules
↓
equivalent expression graph
↓
register allocation
↓
native code

로 생성한다.

이 단계부터 상당히 상용 VM스럽다.

45. SuperOperatorSynthesizer도 자동화 범위를 넓혀야 한다

↓

↓

↓

이게 꽤 강력하다.

최종 판단

이 프로젝트의 문제는 기능이 부족해서가 아니다.

오히려 지금 이미 기능은 아주 많다.

진짜 문제는:

StateMachineDecoder
ContextOffsetScrambler
MicroDispatcher
SuperOperatorSynthesizer
Nested VM
RegisterAssignment

같이 상용급으로 가기 위한 핵심 아이디어들이 소스에는 있는데 production poly_direct commercial path의 중심 구조를 실제로 바꾸지 못하고 있다는 것이다.

현재 production 핵심은 여전히:

stable VM ABI
↓
self-decrypt
↓
central dispatcher
↓
256-entry table
↓
fairly semantic-pure handlers
↓
central dispatcher

이다.

그래서 다음 버전에서 새 암호 알고리즘 하나 더 넣거나 anti-debug check를 늘리는 것보다,

① 중앙 dispatcher 제거
② VM-role 레지스터를 block마다 바꾸기
③ context layout 실제 랜덤화
④ StateMachineDecoder production 통합
⑤ handler semantics 자체를 build마다 합성
⑥ 서로 다른 VM architecture 최소 2~3개 생성

이 여섯 개가 훨씬 중요하다.

이것까지 들어가면 더 이상 **“잘 만든 polymorphic RISC VM protector”**가 아니라, 실제로 “architecture-polymorphic VM protector” 쪽으로 넘어가고, 그 지점부터 Themida/Code Virtualizer와 비교할 때 훨씬 의미 있는 경쟁 구조가 된다.
